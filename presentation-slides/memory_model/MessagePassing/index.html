from familiar mirror pairing to message-passing vocabulary←/→ · N notes · S presenter · O overview
This slide uses a simplified warp-like 4 by 8 tile as intuition. In Vulkan terminology, the real representative case uses shader invocations in a subgroup; "warp" is only a familiar mental model, not a Vulkan API term. The mirror example makes partner pairing concrete: thread 1 and thread 6 are a left-right pair in the first row. Payload is not a single variable; conceptually it is a per-invocation slot in a payload buffer, so payload[1] stores T1's value and payload[6] stores T6's value. Guard is also separate per-invocation synchronization storage; guard[1] is the signal associated with payload[1]. There is no extra swap-style temporary variable in the test. The two endpoints connect through release/acquire: T1 writes payload[1], releases and signals guard[1]; T6 observes/acquires guard[1], then reads payload[1].

In this case bufferCoord = i and partnerBufferCoord = 31 - i — each lane's slot is its own ID, and the partner's slot is the mirrored ID.

Guard was signaled. Acquire must have made the partner payload write visible. The check fires; payload matches expected value, no fail written.

From Shader Observation
to Host Verdict

10 / 15
skip path if (skip) { /* no fail written */ }

Partner guard was not observed

The reader saw guard[partner] still equal to 0. This race instance is not judged. The shader writes nothing to the fail buffer; this invocation contributes no information about memory-model correctness.

Outcome: no fail entry. The case can still pass on this iteration.

fail path if (!skip && r != partnerBufferCoord) { fail[bufferCoord] = 1; }

Guard was observed, payload was wrong

The reader saw guard[partner] non-zero (acquire fired) but the partner payload read returned a stale or incorrect value. The guard promised visibility, but the visibility did not actually carry the payload through.

Outcome: fail entry = 1 at this invocation's slot.

Host-side loop: from fail-buffer entries to a case verdict

1
clear fail buffer
memset(fail, 0, …);
2
clear payload + guard
clearBuffer(payload); clearBuffer(guard);
3
dispatch × 50, 4 submits
vkCmdDispatch(cmd, …);
4
copy fail → host memory
vkCmdCopyBuffer(… fail …);
5
scan fail buffer
any nonzero → case fails

What a failure usually means

  • Release/acquire propagation broken — the guard signal was issued but the prior payload write did not reach the partner.
  • Scope mishandling — synchronization reached the wrong set of invocations (e.g. workgroup scope where subgroup was needed, or vice versa).
  • MakeAvailable / MakeVisible dropped — noncoherent extension-mode cases rely on these bits; a lowered shader that omits them fails this exact path.
  • Storage-class lowering — buffer / image / workgroup / physbuffer handled differently in the back-end; this case is buffer-only and exposes that specific lowering.
  • Shader-compiler issue — barrier or atomic lowering removed the required ordering; vendor compilers must preserve release/acquire across the optimization pipeline.

No tolerance, no partial success: one nonzero entry makes the case fail. Up to 256 failing invocation indices are logged.

storage-class lowering — the compiler rewriting a high-level GLSL storage class (workgroup, image, …) into the actual backend storage (LDS, texture unit, …). barrier / atomic lowering — the compiler translating atomicStore, memoryBarrier, controlBarrier into the actual hardware instruction sequence; release/acquire bits must survive this translation.

How write_after_read
and transitive Differ

12 / 15

Same concepts — payload, guard, skip, fail — but three different ordering questions.

baseline

message_passing

Expected: after the guard is observed, the protected payload is visible.

1write own payload
2release / signal own guard
3acquire partner guard
4read partner payload

Fail when: guard observed, but partner payload is stale or wrong.

timing inversion

write_after_read

Expected: the early payload read stays zero; it must not see the later write.

1early-read partner payload
2synchronize through guard path
3partner writes payload later
4early value must stay zero

Fail when: the early read sees a nonzero value that should not have been visible yet.

visibility chain

transitive

Expected: if the chain is observed, visibility reaches the final payload read through the relay.

1all invocations write payload
2representative release/acquire
3broadcast skip through workgroup
4read partner payload after relay

Fail when: the chain was observed, but the final payload read is stale or wrong.

Part B taught the direct protocol. These nearby families mutate the timing or add a relay, but keep the same CTS pattern: shader detects bad visibility, writes the fail buffer, and the host scans it.

memory_model is broader than release/acquire←/→ · N notes · S presenter · O overview
Page 13 expands from the message_passing-related families to the full memory_model category. The category has five registered families: message_passing, write_after_read, transitive, padding, and shared. The first three are synchronization and visibility tests rooted in vktMemoryModelMessagePassing.cpp and covered by MessagePassing.md. Padding is a different angle: std140 structure copies should write declared scalar members but not corrupt destination padding bytes. Shared is another angle: generated GLSL shared objects inside compute workgroups must preserve values across write, barrier, read, and compare steps for many scalar, vector, matrix, array, nested-struct, 16-bit, and 8-bit layouts. The takeaway is that memory_model is not only release/acquire; it is shader-visible memory correctness from several directions. The category page links these to three Level-3 pages: MessagePassing.md, Padding.md, and SharedLayout.md.
