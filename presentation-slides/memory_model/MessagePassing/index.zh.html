06: Representative Case: The Path We Will Walk Through

  • Chosen because it is a clean case: compute, `u32`, subgroup, buffer payload/guard.
  • `DIM` is like CUDA blockDim.x/blockDim.y for a square block tile: local workgroup size is `DIM × DIM`.
  • `NUM_WORKGROUP_EACH_DIM` is like CUDA gridDim.x/gridDim.y: number of workgroups along each 2D axis.
  • Total launched shader invocations are `(DIM × NUM_WORKGROUP_EACH_DIM)²`, analogous to total CUDA threads in a 2D grid.
  • `DIM = 31` is intentional: large but under common max workgroup invocation limits after `31² = 961`, and non-power-of-two dimensions catch indexing/synchronization bugs that a neat 32 or power-of-two layout might hide.
  • `ext + noncoherent` means explicit MakeAvailable / MakeVisible semantics.
  • Pages 07–10 stay inside this exact path.

08 / 15

如果 lane i 观察到 partner guard i ^ 31，那么 partner payload i ^ 31 必须已经等于 partnerBufferCoord。

在这个 case 中，bufferCoord = i 且 partnerBufferCoord = 31 - i — 每个 lane 的 slot 是自己的 ID，partner 的 slot 是镜像 ID。

1
写入自己的 payload
publisher
payload[bufferCoord] = bufferCoord;

publisher
atomicStore(guard[bufferCoord], 1, …release…);
3
acquire-load partner guard
consumer
skip = atomicLoad(guard[partnerBufferCoord], …acquire…) == 0;
4
除非 skipped，否则检查 partner payload
consumer
r = payload[partnerBufferCoord]; if (!skip && r != partnerBufferCoord) fail[bufferCoord] = 1;

如果 !skip 已观察到

Guard 已发出信号。Acquire 必须已经让 partner payload write 可见。检查会执行；payload 匹配期望值，不写 fail。

如果 skip 未观察到

Partner guard 仍为 0。这个 race instance 不被判定；无论 payload 值如何，都不写 fail。

四个步骤，按 shader 顺序

// Step 1   payload.x[bufferCoord]        = bufferCoord;
// Step 2   atomicStore(guard.x[bufferCoord], 1u, …release+makeAvailable…);
// Step 3   skip = atomicLoad(guard.x[partnerBufferCoord], …acquire+makeVisible…) == 0u;
// Step 4   r = payload.x[partnerBufferCoord];
         if (!skip && r != uint(partnerBufferCoord)) fail.x[bufferCoord] = 1u;
先 payload 后 guard，先 guard 后检查，未观察到则 skip←/→ · N notes · S presenter · O overview

08: Payload Before Guard, Check After Guard

  • Key expected behavior is now safe to state.
  • `skip` is not failure; it means the guard was not observed.
  • This path has no full-group `barrier()` / CUDA-like `__syncthreads()`; progress is judged only when the peer guard is actually seen.
  • Failure only when `!skip` and payload value is wrong.

  • gl_ScopeSubgroup谁可以同步
  • gl_StorageSemanticsBuffer哪个 storage class
  • gl_SemanticsRelease发布之前的 writes
  • gl_SemanticsMakeAvailable将它们推向该 scope

效果：bufferCoord 处先前的 payload write 以 guard 信号为锚点，在 subgroup 内变为 available。

reader

在 guard 之后让 partner payload visible

skip = atomicLoad(guard.x[partnerBufferCoord],
  gl_ScopeSubgroup, gl_StorageSemanticsBuffer,
  gl_SemanticsAcquire | gl_SemanticsMakeVisible) == 0u;
  • gl_ScopeSubgroup谁可以同步
  • gl_StorageSemanticsBuffer哪个 storage class
  • gl_SemanticsAcquire依赖之前的信号
  • gl_SemanticsMakeVisible将 writes 拉入本地视图

效果：观察到 guard 后，partnerBufferCoord 处的 partner payload write 对 reader 变为 visible。

gl_ScopeSubgroup

同步传播范围 — 这里只有该 subgroup 的 32 个 lanes 可以配对。device、queuefamily、workgroup 是其他选择；每种选择都会改变协议含义。

gl_StorageSemanticsBuffer

同步涉及的 storage class — binding 0/1 上的 SSBO。该保证只携带位于 buffer storage 中的 payload writes，而不是 image / workgroup / physbuffer。

scope + storage

ordering 保证只适用于这个精确组合 — payload edge 不会跨越 scope 边界，也不会跳到其他 storage classes。

09: Why the Guard Makes Payload Visible

  • Writer side: Release + MakeAvailable.
  • Reader side: Acquire + MakeVisible.
  • Analogy:
    • write payload: you write a paper
    • release / MakeAvailable: you publish it to arXiv
    • acquire / MakeVisible: your reader downloads it from arXiv
    • read payload: the reader reads your paper
  • `queuefamily` scope roughly means synchronization across queues from the same Vulkan queue family; broader than workgroup/subgroup, but not necessarily all queues/devices.
  • Guarantee is bounded by both scope and storage semantics.

从 Shader 逻辑
到 Host 判定

10 / 15
skip path if (skip) { /* no fail written */ }

Partner guard 未被观察到

Reader 看到 guard[partner] 仍等于 0。这个 race instance 不被判定。Shader 不向 fail buffer 写任何内容；这个 invocation 不提供 memory-model correctness 信息。

结果：无 fail entry。这个 case 在本轮 iteration 仍可通过。

fail path if (!skip && r != partnerBufferCoord) { fail[bufferCoord] = 1; }

Guard 已被观察到，但 payload 错误

Reader 看到 guard[partner] 为非零（acquire 触发），但读取 partner payload 返回了 stale 或错误值。Guard 承诺了 visibility，但 visibility 实际上没有把 payload 带过来。

结果：在该 invocation 的 slot 上写入 fail entry = 1。

Host-side loop：从 fail-buffer entries 到 case 判定

1
清空 fail buffer
memset(fail, 0, …);
2
清空 payload + guard
clearBuffer(payload); clearBuffer(guard);
3
dispatch × 50，4 次 submits
vkCmdDispatch(cmd, …);
4
复制 fail → host memory
vkCmdCopyBuffer(… fail …);
5
扫描 fail buffer
任一非零 → case 失败

失败通常意味着什么

  • Release/acquire propagation broken — guard 信号已发出，但之前的 payload write 没有到达 partner。
  • Scope mishandling — synchronization 到达了错误的一组 invocations（例如需要 subgroup scope 时用了 workgroup scope，或反过来）。
  • MakeAvailable / MakeVisible dropped — noncoherent extension-mode cases 依赖这些 bits；lowered shader 如果省略它们，就会在这个精确路径上失败。
  • Storage-class lowering — buffer / image / workgroup / physbuffer 在 back-end 中处理方式不同；这个 case 仅涉及 buffer，暴露的是该特定 lowering。
  • Shader-compiler issue — barrier 或 atomic lowering 移除了所需 ordering；vendor compilers 必须在 optimization pipeline 中保留 release/acquire。

没有容忍度，也没有部分成功：一个非零 entry 就会让 case 失败。最多记录 256 个失败 invocation indices。

storage-class lowering — compiler 将高层 GLSL storage class（workgroup、image 等）重写为实际 backend storage（LDS、texture unit 等）。 barrier / atomic lowering — compiler 将 atomicStore、memoryBarrier、controlBarrier 翻译成实际硬件指令序列；release/acquire bits 必须在该翻译中保留下来。

shader 写 fail buffer，host 扫描 fail buffer←/→ · N notes · S presenter · O overview

10: From Shader Observation to Host Verdict

  • Host does not directly judge payload values; shader writes fail buffer.
  • Fail buffer is cleared, shader runs many times, host scans for any nonzero entry.
  • One nonzero entry fails the CTS case.

baseline

message_passing

2release / signal own guard
3acquire partner guard
4读取 partner payload

Fail when：guard 已被观察到，但 partner payload stale 或错误。

write_after_read

Expected：early payload read 保持为 zero；它不能看到之后的 write。

1early-读取 partner payload
2通过 guard path 同步
3partner 稍后写 payload
4early value 必须保持 zero

Fail when：early read 看到了本不应可见的非零值。

visibility chain

transitive

Expected：如果 chain 被观察到，visibility 通过 relay 到达最终 payload read。

1所有 invocations 写 payload
2representative release/acquire
3通过 workgroup broadcast skip
4读取 partner payload after relay

Fail when：chain 已被观察到，但最终 payload read stale 或错误。

Part B 讲的是直接协议。这些相邻测试子族改变时序或增加 relay，但保持同一个 CTS 模式：shader 检测错误 visibility，写 fail buffer，然后 host 扫描它。

12: How `write_after_read` and `transitive` Differ

  • `write_after_read`: early read must not see the later synchronized write.
  • `transitive`: visibility can be carried through a representative + workgroup relay.
  • These are contrast cases, not full new walkthroughs.
