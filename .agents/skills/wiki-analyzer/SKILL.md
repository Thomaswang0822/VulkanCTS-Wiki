# Vulkan CTS Wiki Analyzer

This skill analyzes Vulkan CTS tests and generates structured wiki documentation.

## When to Invoke

Invoke this skill when:
- User wants to document a test category
- User wants to understand the structure of tests
- User wants to create documentation for a category

## Prerequisites

**CRITICAL**: Before starting any documentation work, you MUST read:

1. **Progress tracker**: `external/vulkancts/wiki/README.md`
   - Check the progress table to see which categories are done
   - Know where to continue from previous sessions

2. **Objectives file**: `external/vulkancts/wiki/Objectives.md`
   - Contains the top-level requirements for documentation
   - Defines what questions the documentation must answer

3. **Official test plan**: `doc/testspecs/VK/apitests.adoc`
   - Contains official Vulkan API test specifications
   - Provides authoritative information about test purposes

## Execution Model

### One Run = One Category

Each invocation of this skill processes **one complete category**:

```
One Run = 1 Level-2 Document + N Level-3 Documents
```

**Example for "api" category**:
- Create `wiki/categories/api.md` (Level-2)
- Create `wiki/testfiles/api/vktApiBufferTests.md` (Level-3)
- Create `wiki/testfiles/api/vktApiCopiesAndBlittingTests.md` (Level-3)
- Create `wiki/testfiles/api/vktApiCommandBuffersTests.md` (Level-3)
- ... (all 49 test files in api directory)

### Parallel Execution

If you have orchestrator capability:
1. Identify all CPP test files in the category directory
2. Launch parallel worker agents to create Level-3 documents
3. Wait for all workers to complete
4. Create the Level-2 document summarizing all test files

### After Completion

Update the progress table in `wiki/README.md`:
- Mark the category as ✅ Done
- Update statistics

## Documentation Levels

### Level 2: Category Documentation

**Purpose**: Document each top-level test category.

**Naming**: `wiki/categories/{category_name}.md`

**Contents**:
- Overview of what the category tests
- List of all CPP test files in the category
- Key test families and their purposes
- Common patterns and principles
- Links to Level-3 documentation

### Level 3: CPP Test File Documentation

**Purpose**: Document all tests generated by one CPP file.

**Naming**: `wiki/testfiles/{category}/{cpp_filename}.md`

**Reference Example**: [vktApiCopiesAndBlittingTests.md](../external/vulkancts/wiki/testfiles/api/vktApiCopiesAndBlittingTests.md)

**Contents** (keep concise):
- Overview (1-2 sentences)
- Source code link
- Test hierarchy (ASCII tree)
- Test families list with brief descriptions
- Parameter dimensions (table format)
- Key source files (if the file includes other files)
- Verification methods (brief list)
- Test principles (bullet points)

## Analysis Process

### Step 1: Read Prerequisites

```
1. Read external/vulkancts/wiki/README.md (check progress)
2. Read external/vulkancts/wiki/Objectives.md
3. Read doc/testspecs/VK/apitests.adoc
```

### Step 2: Identify Category

From user input or test name, identify the category (e.g., "api", "memory", "pipeline").

### Step 3: Find All CPP Test Files

Locate all `vkt*Tests.cpp` files in:
```
external/vulkancts/modules/vulkan/{category}/
```

### Step 4: Create Level-3 Documents

For each CPP file:
1. Read the file to understand its structure
2. Identify test families and parameters
3. Create concise documentation following the reference example

### Step 5: Create Level-2 Document

Summarize all Level-3 documents into one category document.

### Step 6: Update Progress

Update `wiki/README.md` progress table.

## Key Principles

1. **CPP files are primary reference**: Each Level-3 doc maps 1:1 to a CPP file
2. **No parameter explosion**: Never expand to individual tests; stop at test families
3. **Concise Level-3 docs**: Keep them brief and scannable
4. **Direct code links**: Always link to specific code lines
5. **DRY**: Don't repeat information across documents
